最近在 `pi`（coding agent）里折腾了一把 `swarm` skill，想弄清楚一个很实际的问题：**在完全相同的模型和思考强度下，花更多 Token 跑多 Agent 协作（Swarm），到底比单 Agent 直接干活强在哪？还是只是“花大钱办小事”？**

我用 `deepseek-v4.1-flash`（思考强度 `high`）完整跑了两轮对比实验，解析了 `pi` 的会话日志，也亲自上手体验了两边的成品。

结果挺出乎意料：**第一轮我以为 Swarm 翻车了；第二轮把变量控严之后，Swarm 反而全面反转，甚至比单 Agent 交卷更快。**

---

## 第一轮实验：一次“失败”的对照，却暴露了 Swarm 最大的坑

第一轮我给了一句非常模糊的提示词：

> 制作一个介绍 pi coding agent 的 UI

然后分别在 `normal/`（单 Agent）和 `swarm/`（Swarm 模式）里开跑。最后看日志数据，第一眼差点直接给 Swarm 判死刑：

| 指标 | 单 Agent（`normal`） | Swarm 模式（`swarm`） | 对比 |
| :--- | :---: | :---: | :---: |
| 墙钟用时 | 27 分 18 秒 | **2 小时 5 分 45 秒** | 4.6× |
| 有效用时（扣等待） | **20 分 8 秒** | **2 小时 5 分 45 秒** | **6.2×** |
| Assistant 轮次 | 93 turns | 430 turns | 4.6× |
| 总 Token | 6.87M | 52.24M | **7.6×** |
| 估算费用 | $0.0880 | $0.5025 | 5.7× |

两份成品的差距也很有意思：
- `normal` 做了一个暖纸白底的中文极简文档站，带交互式 Agent Loop 步进器、请求上下文分层图，甚至手写了桌面/移动双端可点击的 JSONL 会话树 SVG；

![第一轮 normal 成品](/images/pi-swarm-vs-single-agent/exp1-normal.png)

- `swarm` 做了一个深色暗黑极客风的**全英文**官网，带终端打字动画、5 步多平台 Quickstart、27+ Provider 列表、快捷键速查表，零构建依赖。

![第一轮 swarm 成品](/images/pi-swarm-vs-single-agent/exp1-swarm.png)

但翻开会话日志后，我发现**这根本不算一次公平的对照实验**：
1. **`normal` 并不是真正的盲写直出**：它在开工前先调了 `ask_user_question`，跟我对齐了需求，我选择了「Vite + React」、「极简文档风」和「只做核心特性 + 架构」。有了这三刀收敛，它直接跳过所有冗余板块，把 20 分钟全砸在了核心交互上。
2. **`swarm` 跳过对齐直接开干了**：Coordinator 自己脑补了一套“英文全功能开源官网”的规格，接着 `builder` 和 `verifier` 围绕 390px 换行、打印样式、单句措辞来回打回了 3 轮，整整烧了 2 个小时。

**第一轮虽然实验失真，却得出了一个教训：**
> **永远不要把一句模糊的 Prompt 直接丢给 Swarm。** 单 Agent 遇到模糊需求还会停下来问你；Swarm 一旦进入编排模式，很容易跳过澄清直接拆角色派活——方向一旦猜偏，它就会用 6 倍的时间和 7 倍的 Token，帮你精雕细琢一个你根本没要的方案。

## 第二轮实验：严格控制变量，换一道更能测出真本事的题

为了做一次真正公平的 A/B 对比，我重新设计了第二轮实验(氖吉米协助设计)：

- **题目升级为交互式单页工具**：「Cron 表达式可视化调试器」（标准 5 位 Cron、表达式 ↔ 可视化构建器双向联动、中文自然语言释义、未来 10 次触发时间与时区切换、语法精准报错、预设模板、URL 分享）。既有视觉与交互动线要求，又藏着一堆经典逻辑边界（Vixie Cron OR 语义、周日 `0/7` 等价、闰年 `0 0 29 2 *`、永不触发 `0 0 31 2 *` 防死循环、夏令时 DST）。
- **彻底控制变量**：
  - 两组拿到**一字不差的详尽 Spec**；
  - 明确要求**简体中文交付、全程禁止提问直接干到底**；
  - **0 人工干预**，不限制技术栈，也不给 Swarm 设轮次上限；
  - 统一 `deepseek-v4.1-flash`（`thinking = high`）。

### 日志结果直接反转：Swarm 反而更快交卷

| 指标 | 单 Agent（`normal`） | Swarm 模式（`swarm`） | 对比（`swarm / normal`） |
| :--- | :---: | :---: | :---: |
| 墙钟 / 有效用时 | 39 分 31 秒 | **32 分 47 秒** | **0.83×（快了 6 分 44 秒）** |
| 总轮次 | 79 turns | 356 turns（主 69 + 5 workers） | 4.51× |
| 总 Token | 15.51M | 32.17M | 2.07× |
| Output Token | 224k | 414k | 1.85× |
| 估算费用 | **$0.2088** | **$0.4664** | **2.23×** |

这次两组都不约而同选择了**零构建依赖的原生 HTML + CSS + JS**，离线双击就能跑，8 个核心边界用例在 Playwright 浏览器实测下全部无报错、无卡死、1440px / 390px 零横向溢出。

但深入拆解过程和成品后，Swarm 这一轮的表现确实让人眼前一亮。

## 为什么第二轮 Swarm 赢了？

### 1. 契约先行 + 真正跑通了并行提速

翻看第二轮的 `board.jsonl`，Swarm 这次的协作非常教科书：
- Coordinator 先起草了一份 `CONTRACT.md`，把 DOM ID、CSS 类名、JS 模块接口全部写死；
- 然后瞬间拉起 4 个职责严格隔离、互不碰对方文件的作者并行开工：
  - `core`（4 分 14 秒）：解析引擎、Vixie 语义、时区与触发计算
  - `desc`（4 分 38 秒）：中文自然语言释义
  - `shell`（26 分 20 秒）：HTML 结构与深色响应式样式
  - `logic`（26 分 21 秒）：双向构建器与页面状态编排
- 同期拉起独立 `verifier`（24 分 41 秒），等 `core` 完事就开始写第一阶段测试，全部合拢后再跑全量静态审计与 Playwright E2E。

单 Agent 只能串行推进，越到后期上下文越重，总共跑了近 40 分钟；而 Swarm 靠并行把端到端交付压到了 **32 分 47 秒**，费用倍率也从第一轮夸张的 5.7× 降到了非常健康的 **2.23×**（多花两毛多美金）。

### 2. 独立 Verifier 真抓出了肉眼可见的 Bug

两组都写了自动化测试，但覆盖深度不在一个量级：
- `normal` 写了 40 项引擎单元测试；
- `swarm` 产出了 **1,200+ 项单元与静态断言 + 30 项 Playwright E2E 测试**。

更重要的是，Swarm 的 `verifier` 不是走过场——在验收截图阶段，它实打实抓出了两个连单 Agent 自己写完都容易忽略的 UI 语义 bug，并派单给 `logic` 和 `shell` 闭环修掉了：
1. 错误列表渲染时，标签里的字段名和报错文案开头的字段名重复了；
2. 未来触发时间表的后续行，原本全用 `timestamp - Date.now()` 导致显示成“间隔 11 小时 55 分”，修正为第一行显示倒计时、后续行显示相邻两次触发的真实间隔，并同步把表头改成了「倒计时 / 间隔」。

## 总结：什么时候该用单 Agent，什么时候该上 Swarm？

两轮实验跑下来，结论其实非常清晰：

1. **需求还不清楚、需要边聊边定方向时 → 必须先用单 Agent 对齐**
   - 直接把模糊需求扔给 Swarm，就是在放大返工成本。先和单 Agent 聊透风格、范围和技术边界，甚至先产出一份 Spec，再决定要不要上 Swarm。
2. **小型探索性页面、追求极低成本时 → 单 Agent 性价比最高**
   - 单 Agent 能省掉一半以上的 Token，且上下文高度统一，适合轻量任务和快速原型。
3. **Spec 已经清晰、能拆出明确模块契约、且对逻辑边界与交互质量有高要求时 → 放心上 Swarm**
   - 一旦有了清晰的 Spec 和契约拆分，Swarm 不仅不会更慢，反而能靠并行**比单 Agent 更快交卷**，同时用 ~2× 的 Token 成本换来更清爽的架构解耦、更扎实的自动化测试，以及真正能抓出真实 Bug 的独立验收闭环。
